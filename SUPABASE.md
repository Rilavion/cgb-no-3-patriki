# Настройка Supabase для сайта ЦГБ №3

## 1. Применение схемы

1. Откройте проект в Supabase.
2. Перейдите в **SQL Editor**.
3. Скопируйте содержимое `supabase-migration.sql` и выполните его целиком.
4. Миграция выполняется в транзакции: при ошибке изменения откатываются целиком. Повторный запуск дополняет совместимые таблицы, обновляет функции и пересоздаёт политики без удаления контента.

Перед первым запуском в рабочем проекте сделайте резервную копию. Если у существующих таблиц другие типы ключей или уже есть дублирующиеся `id`, создание уникальных индексов остановит миграцию и транзакция откатится — сначала исправьте конфликтующие данные.

Миграция создаёт и настраивает:

- `news` — публикации;
- `faq` — вопросы и ответы;
- `info_page` — редактируемая страница о больнице;
- `custom_roles` — определения ролей;
- `user_roles` — роли пользователей;
- функцию `staff_upsert_role` для назначения ролей;
- серверную проверку разрешений `cgb_can`, согласованную с интерфейсом;
- автоматическое создание роли `user` после регистрации;
- RLS-политики и необходимые права.

## 2. Назначение первого администратора

Сначала создайте пользователя в разделе **Authentication → Users**. Затем выполните в SQL Editor запрос, заменив адрес электронной почты:

```sql
insert into public.user_roles(user_id,role,display_name)
select id,'admin','Администратор'
from auth.users
where lower(email)=lower('admin@example.org')
on conflict (user_id) do update set
  role='admin',
  display_name=excluded.display_name,
  updated_at=now();
```

Запрос должен затронуть одну строку. После этого выйдите из сайта и войдите снова либо обновите страницу.

## 3. Клиентская конфигурация

`config.js` должен содержать только URL проекта и браузерный publishable key:

```js
window.SUPABASE_CONFIG={
  url: "https://PROJECT_REF.supabase.co",
  anonKey: "PUBLISHABLE_KEY"
};
```

Publishable key разрешено использовать в браузере: доступ ограничивают RLS-политики из миграции. Никогда не добавляйте в репозиторий secret key или service-role key.

## 4. Модель доступа

- Любой посетитель может читать новости, FAQ и страницу о больнице.
- `staff` может создавать и редактировать новости, а также управлять FAQ.
- Только `admin` может удалять новости, редактировать страницу о больнице, назначать роли и изменять определения ролей.
- Пользователь видит собственную запись роли; администратор видит список всех ролей.
- Для дополнительных ролей разрешения из `custom_roles.permissions` проверяются не только интерфейсом, но и RLS через `cgb_can`. Поддерживаются точные правила и шаблон `"*"`, например `{"news":{"edit":true}}` или `{"*":{"*":true}}`.
- Разрешение `staff:view` открывает чтение списка ролей пользователей, но назначать роли по-прежнему может только `admin`.

Проверяйте изменение прав в новой сессии пользователя: уже открытая вкладка может некоторое время отображать ранее загруженное состояние интерфейса, хотя серверные RLS-проверки применяются сразу.

## 5. Проверка после миграции

В SQL Editor убедитесь, что базовые записи созданы:

```sql
select key,name,permissions from public.custom_roles order by sort;
select id,jsonb_typeof(data) as data_type from public.info_page where id=1;
select tablename,policyname from pg_policies
where schemaname='public'
  and tablename in ('news','faq','info_page','custom_roles','user_roles')
order by tablename,policyname;
```

Затем проверьте сайт в трёх отдельных сеансах: без входа, под `staff` и под `admin`. Publishable key не обходит RLS, поэтому операции должны соответствовать модели доступа выше.
