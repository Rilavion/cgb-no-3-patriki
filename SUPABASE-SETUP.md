# ЦГБ №3 — Настройка базы данных Supabase

Сайт уже подключён к проекту (ключи лежат в `config.js`, их менять не нужно).
В базе сейчас есть только таблицы ролей и контента (`user_roles`, `custom_roles`,
`faq`, `info_page`, `news`). Остальные ~45 таблиц, функции и права нужно создать
одним скриптом.

## Шаг 1. Выполнить SQL

1. Открой https://supabase.com/dashboard → свой проект.
2. Слева **SQL Editor** → **New query**.
3. Открой файл **`SUPABASE-SETUP.sql`** (лежит рядом), скопируй ВЕСЬ текст,
   вставь в редактор и нажми **Run** (Ctrl+Enter).
4. Supabase покажет предупреждение **«Potential issues detected»** —
   это нормально: оно срабатывает из-за служебных команд `drop policy if exists`
   и `revoke`. Ничего не удаляется и не ломается. Жми **«Run without RLS»** —
   RLS скрипт включает сам вместе с политиками доступа (блок 3).
5. Внизу должно быть `Success. No rows returned` — ошибок быть не должно.

Скрипт можно запускать повторно — ничего не сломается: таблицы создаются
только если их нет, а политики пересоздаются.

## Что делает скрипт

| Блок | Содержимое |
|---|---|
| 1 | Все таблицы: заявления, жалобы, заявки, нарушения, проверки АБ, отчёты, поставки, тесты, премирование, Discord-кэш и пр. |
| 2 | RPC-функции, которые вызывает сайт (подача жалоб/заявок/поставок/тестов, назначение ролей, черновики премирования) |
| 3 | Права: чтение — всем посетителям, запись — только авторизованным сотрудникам; роли — только через админку |
| 4 | Realtime для таблицы `applications` — чтобы Discord-бот мгновенно видел решения по заявлениям |

## Шаг 1.5. Назначь себя администратором ⚠️ ВАЖНО

Без этого шага ты **не увидишь служебные разделы** на сайте — они скрываются
системой прав. Доступ определяется таблицей `user_roles`: полный доступ даёт
роль `admin`.

1. Supabase → **Authentication → Users** → найди свой email → скопируй **UUID**.
2. SQL Editor → выполни (подставив свой UUID):

```sql
insert into public.user_roles (user_id, role, display_name)
values ('ТВОЙ-UUID-СЮДА', 'admin', 'Главный врач')
on conflict (user_id) do update set role = 'admin';
```

3. Обнови сайт (Ctrl+F5) → войди → в меню появятся «Мои заявки» и «Служебное»
   полностью, а в Личном кабинете — панель «Роли пользователей» с кнопкой
   «+ Создать аккаунт» для добавления сотрудников.

> Дальше роли остальным выдаются уже через сайт: Личный кабинет →
> «Роли пользователей». Названия и бейджи ролей берутся из твоей таблицы
> `custom_roles` (у каждой роли должна быть колонка `base_role`
> = `admin` / `ss` / `user` — скрипт её добавляет, если её не было).

## Шаг 2. Проверка

1. **Table Editor** — должны появиться все таблицы (applications, complaints,
   requests, vp_checks, tests, payroll_drafts и т.д.).
2. Зайди на сайт под своим аккаунтом → боковое меню → должны открываться
   служебные разделы без ошибок «таблица не найдена».
3. Если на какой-то странице видишь ошибку вида
   `relation "public.xxx" does not exist` — значит скрипт не выполнился целиком:
   выполни его ещё раз полностью.

## Права доступа (кратко)

- **anon (гость)**: читает новости, уставы, состав, автопарк, FAQ, материалы;
  подаёт жалобы/заявки/поставки и проходит тесты через RPC-функции.
- **authenticated (сотрудник)**: полный доступ к служебным таблицам.
  Кто что видит на сайте — регулируется ролями на странице «Роли».
- **service_role (бот)**: обходит все ограничения. Ключ вставляется ТОЛЬКО
  в `.env` бота, никогда не публикуется.

## Важно про email-подтверждения

Для внутреннего сайта удобно отключить подтверждение email, иначе Supabase
ограничивает отправку писем (~4 в час):
**Authentication → Providers → Email → выключить «Confirm email»**.

После этого страница «Роли» сможет создавать пользователей сразу,
а восстановление пароля будет работать через magic-link-настройки SMTP
(или попроси сменить пароль через Dashboard → Authentication → Users).
